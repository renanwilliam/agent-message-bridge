# Message retention and unlimited conversations

## Runtime contract

There is no configured lifetime message ceiling. Old JSON configurations with `limits.maxTurns: 20` (or another previously valid value) still parse, but this field is ignored. Do not rewrite private configuration or credentials to remove it. Per-sender minute quotas, authorization, atomic publication, leases, fencing and delivery attempt limits remain. Choosing a new conversation does not bypass the rate quota. Counts use JavaScript safe integers; numeric exhaustion fails closed instead of wrapping, an implementation integrity bound rather than a product turn quota.

Messages are visible until exactly `Date.parse(message.timestamp) + 14 * 24 * 60 * 60 * 1000`, exclusive. Reads, duplicate publication, claim, completion and acknowledgement apply this deadline to legacy and new messages. A new response has its own original publication timestamp; it does not renew its parent's retention. The worker checks the original notice timestamp before delivery and immediately before invoking POST. A network call initiated before the deadline can finish later. No service can retract already delivered information.

The optional **top-level** `retentionExpiresAt` is a nonnegative integer Unix timestamp in **seconds**, rounded up from the millisecond visibility deadline. It is never derived from auth `expiresAt`, claim `leaseUntil`, subscription renewal or retry time. Store methods intentionally return raw expired rows for CAS and operational cleanup; application methods enforce visibility. SQLite migrates its schema additively and persists the field but has no automatic physical TTL sweeper; MemoryStore is also not a physical retention service. SQLite operators need a separately approved cleanup/backup policy.

| Record | New-write physical deadline | Logical behavior |
| --- | --- | --- |
| history `message#…` and `id#…` | Original message +14 days, both copies | No text after deadline through supported APIs |
| sender dedup | Original message +14 days | No expired text replay; terminal 410 when reference/expired row remains |
| claims, running and done | Parent message +14 days | Cannot claim, complete or acknowledge an expired parent; lease capped at deadline |
| outbox, pending/done/dead | Source message +14 days | No new POST after deadline check; expired pending rows become dead with no `dueAt` |
| inbox, when enabled | Source message +14 days | Pending discovery filters original logical expiry and completed claims; no message text |
| rate counters | End of their minute window +14 days | Existing minute-based rate enforcement unchanged |
| conversation `meta` | **No TTL** | Minimal participants/ACL, original correlation identifier, turn count and global fence counter remain |
| authorization, grants, subscriptions, signing secrets, callback anti-replay | **No change** | Existing security lifecycle remains, separately governed |

Minimal conversation identity metadata is deliberately permanent: deleting it would permit conversation-ID takeover, reset turn numbers, break authorization and allow old claim tokens to become valid again. It contains no message text. Security records are not conversation content and must not be silently assigned history TTL. These exceptions mean this change does not bound every record in the database. Each new conversation can leave one identity record indefinitely.

History pages may be empty while carrying a cursor. Continue until **cursor is absent**, not until `messages` is empty. Cursors remain scoped to the partition/prefix and still work after rows they point to are removed. Queries scan a bounded page; they do not scan all legacy history in a single request. Large turn keys preserve lexical ordering across the original ten-digit key range.

Use globally fresh message IDs. While an expired dedup or `id#` record still exists, the server rejects its retry with 410 `message_expired`. A missing referenced message also returns terminal 410 rather than repeated 503. Once both records are physically gone, an ID can be used again, but it is a **new publication**, not lifetime idempotency. After Phase B, a UUID generation separates new claim addresses and event IDs from old remnants. The permanent conversation-wide monotonic claim fence prevents an old fence matching a later incarnation. Metadata survives retention so turns never reset. Concurrent publication and claim allocation serialize via the same metadata CAS.

Legacy messages keep their original claim key. On the first claim requiring a new fence, an uninitialized legacy metadata counter is bootstrapped by paging history and reading its claim rows. This can be expensive for a large old conversation; initialize these counters in the reviewed migration before rollout where needed. Existing valid legacy claim tokens remain usable until lease/message expiry. Old writers may coexist only with Phase A, which understands generation but never emits it. The supported two-release rollout below requires no subscription or service pause.

## Rollout: distinct application and infrastructure changes

This patch does **not** enable TTL, mutate a live table, backfill old rows, change IAM or delete existing history. The application changes logical visibility for old messages immediately on activation, but does not physically purge them. Claims preserve an existing TTL (including an approved backfill grace); creating or updating an untagged legacy claim assigns its original parent timestamp +14 days. This requires approval covering existing history before TTL activation and prevents future claims on legacy messages from remaining unbounded. Outbox updates preserve existing TTL and leave untagged legacy rows for the reviewed backfill. Expired pending legacy deliveries become dead without deleting their row. The template deliberately leaves TTL disabled. Production CD clones the live template and only changes Code/release metadata; adding TTL in source would not activate it. Do not weaken the CD guard or add broad database permissions to its role.

1. Roll out two separately reviewed application releases through the existing code-only CD, without pausing subscriptions or stopping service:
   - **Phase A:** `src/release-protocol.ts` sets `EMIT_MESSAGE_GENERATION = false`. Every runtime understands both claim addresses, new TTL metadata, logical expiry and fencing, but publishes legacy messages with no generation. Old/A writers therefore contend on the same `claim#id` row. Legacy event IDs are unchanged. During mixed old/A deployment, old readers still have the old visibility policy and old writers can drop TTL or `claimFence` metadata. Keep physical TTL **disabled** and do not backfill/delete anything yet.
   - Verify the exact Phase A release on **all six functions**, including every writer and worker, and wait at least the maximum old invocation lifetime after the last function update, while normal requests and subscriptions continue. Verify no old aliases/versions/event-source targets remain active. The wait is natural draining, not a service pause. Existing MCP sessions, subscriptions and queued work are not cancelled or recreated. Do not proceed from a partial deployment.
   - **Phase B:** set only the reviewed release constant to `true`, enabling generation on new publications. A/B overlap is safe because both already understand the generation claim address. Never deploy B directly over pre-A code. Phase A remains a protocol-compatible rollback target for B while TTL is disabled; pre-A is not safe after any B message exists.
   - Verify all six functions and naturally drain outstanding A invocations before inventory/backfill/TTL activation. Messages published by pre-A or A are included in the legacy inventory, including all missing TTL fields from old rewrites. Runtime tests exercise old/A and A/B concurrent claims and completions, old TTL/highwater erasure, and stable legacy event IDs.
   - After convergence, every reader enforces the cutoff. Inventory or separately approve exports before rollout if older content needs preservation; this release does not delete it physically.
2. Inventory the exact table, current TTL attribute/state, PITR recovery window, backups and export destinations using read-only operator access. Do not infer the target from a public example. Record counts by partition kind, timestamps, versions, dangling references, duplicate IDs and malformed dates. Store private inventory outside the public repository without secrets or message text.
3. Establish a migration cutover `T0` and approve legacy backfill explicitly. Standard history/associated-record deadlines use `ceil((original timestamp +14 days)/1000)`; rate counters use the end of their minute window +14 days. Rows already older than that become eligible for asynchronous deletion when tagged and TTL is enabled, so obtain explicit approval for existing data rather than silently treating this as a new-write-only change. Until that approval, preserve legacy rows untagged. If the installation owner instead requests a physical preservation grace, record a separate approved deadline such as `max(original deadline, T0 +14 days)`; logical visibility remains original timestamp +14 days. Never apply such grace to future writes or renew it on retry. This source patch does not perform either backfill.
4. Before any legacy claims/history can disappear, initialize each conversation's permanent `claimFence` to at least the maximum existing claim fence, while retaining participants, correlation and count. Do this after Phase B convergence and natural drain so no old metadata writer can remove the initialized high-water mark. Use an operator inventory of **all claims**, including orphans, not only the application's history-based bootstrap. Reconcile missing metadata and dangling references first. Conditional writes must match original versions; conflict means re-read/re-evaluate, never overwrite concurrent publication or claim allocation. This is a data migration, not a new runtime IAM privilege. Do not backfill until all legacy writer invocations have finished naturally and no legacy version receives new traffic and counter initialization is verified.
5. Build a dry-run manifest pairing **both text copies** (`message#` and `id#`) with their exact original timestamps and dedup pointers. Bind claims to the exact parent, outbox to original notice timestamp, and rate records to their minute window. Do not infer message time from leases, last retry, current time, counter values or subscription expiry. Missing/invalid parents or timestamps are quarantined for operator review; do not guess or silently delete them. Never assign this attribute to `meta`, authorization, grants, subscriptions, secrets or callback anti-replay records.
6. Approve the manifest, exact retention deadlines, any requested grace period, affected records, backup/export policy, reconciliation rules and separate infrastructure change. Implement a resumable, rate-limited backfill with version-checked updates, bounded batches, dry-run by default, explicit table/account verification and audit checkpoints. Do not overwrite a newer TTL or extend new-write retention by applying legacy grace to records created after T0. Source timestamps always govern logical visibility even when legacy grace delays physical cleanup. No executable backfill is bundled in this patch.
7. With a separately authorized operator, enable DynamoDB TTL **only on `retentionExpiresAt`**, through a reviewed infrastructure migration/ChangeSet or approved operator action. Equivalent resource property for a separately reviewed template:

   ```yaml
   TimeToLiveSpecification:
     AttributeName: retentionExpiresAt
     Enabled: true
   ```

   No other TTL attribute is safe. Keep deletion protection, retention-on-replacement, encryption, PITR, IAM and auth unchanged. The code-only CD role need not and must not gain `UpdateTimeToLive`. Review infrastructure drift after any direct operator change and reconcile through the appropriate infrastructure owner.
8. Verify the TTL status transitions to enabled on the correct attribute, then observe bounded synthetic canaries: exact application cutoff, both copies eventually gone, no delivery after deadline, expired due candidates stop blocking live work, no counter reset, and no change to subscriptions/authorization. TTL is eventually consistent and may take days to delete eligible items. Monitor actual deleted-item metrics and remaining expired items rather than assuming activation means deletion.

Do not roll back to a reader without the logical cutoff after TTL activation; delayed physical deletion could re-expose data. A code rollback also cannot reconstruct expired records. Preserve a compatible reader or disable serving until reviewed recovery is complete. After restore, reapply current logical visibility and reconcile TTL/metadata before enabling traffic.

## Physical deletion is not an exact 14-day promise

DynamoDB TTL is asynchronous and can delete days after expiry. It does not remove content from existing PITR windows, on-demand snapshots, exports, logs, queues, recipients, client caches or external backups. Inventory and govern these copies separately. A deployment with a 35-day PITR window can retain recoverable older text beyond 14 days even after primary rows disappear. Do not shorten or disable that recovery protection without separate approval. No live TTL, migration or restore verification is claimed by the local tests.
